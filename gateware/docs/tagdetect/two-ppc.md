# TwoPPC connected-component pipeline

`TwoPPC` is the streaming linked-run CCA engine used twice by the hierarchy. It
accepts two horizontally adjacent binary pixels per active clock, assigns and
repairs provisional run labels, accumulates optional features, and emits a
component when its final label closes.

## Architecture

Only the previous row and current run state are needed. Provisional labels are
row-local and are recycled at each end-of-line. Linked label, head, tail, and
feature memories resolve equivalences without storing a full-frame label map.
Forwarding and repair records cover synchronous RAM read-after-write hazards so
that active raster input can continue at one pair per clock.

The feature payload is elaboration-time configurable. The hierarchy uses two
specializations:

- outer: hole fill, feature-presence tracking, and child-list IDs;
- inner: area and centered intensity moments, with pair-fused accumulation.

Bounding boxes, area, presence, moments, feature-coordinate override, and
child tracking can otherwise be independently selected.

## Pipeline stages

Every instantiated stage has a distinct role:

### `TwoPPCS0Stage`

Tracks raster position, reads the previous-row neighborhood, clips the outer
image boundary, and optionally performs streaming one-pixel hole fill. It owns
the end-of-row drain counter and therefore drives `in_ready`. The fixed drain
interval is ten clocks.

### `TwoPPCS1Stage`

Detects new run starts in the two-pixel neighborhood and issues provisional
labels. The label counter resets at end-of-line.

### `TwoPPCS2Stage`

Registers the neighborhood, feature sidebands, and provisional-label request
so the following synchronous label-table reads have a stable request stage.

### `TwoPPCS3Stage`

Reads the current and previous row's link/head state. It applies recent repair
records and write forwarding before returning label metadata. Separate memory
banks and guarded addresses preserve the row-local table invariant.

### `TwoPPCS4Stage`

Converts the neighborhood and repaired label metadata into an ordered token.
It applies the newest tail, head, and feature repairs so the service stage sees
one coherent logical component even when physical RAM updates are still in
flight.

### `TwoPPCS5Stage`

Is the main component service stage. It joins or extends runs, updates selected
feature fields, generates component-close events, and reports outer child
parent/merge relationships. Pair-fused moments share arithmetic between the
two lanes. Live feature-data sources are selected with ordinary logic; the
service stage does not use multiplier or DSP resources as selectors.

### `TwoPPCS6BStage`

Registers and coalesces the writes generated by the service stage. Independent
next-link updates are kept when their addresses differ and collapsed when they
refer to the same label. Its final output is the retired component feature.

## Scheduling and boundaries

End-of-line is the geometry authority; the retained start-of-frame input is
compatibility metadata. The source must stop between rows while `in_ready` is
low. TagDetect guarantees a ten-clock interval after each composite row, and
the outer hole-fill flush is absorbed by the end-of-line ready bubble.

The label table depth must cover the maximum number of provisional runs in a
single row. One all-ones label can serve as an unmapped sentinel when the table
does not consume the complete power-of-two code space. A full power-of-two
table retains an explicit mapped bit instead.

Pair-fused centered moments require hole fill to be disabled, which is why the
optimization is used only by the inner CCA. Address-range guards and stage
repair ordering are correctness invariants; reducing the row gap or table
depth without rerunning the focused parity tests is unsafe.
